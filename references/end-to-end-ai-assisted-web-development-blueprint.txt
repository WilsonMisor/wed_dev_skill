========================================================================
0. HOW TO USE THIS BLUEPRINT
========================================================================

Purpose
- Use this as a master execution blueprint for any serious website or web application.
- Adapt the tasks by website type: marketing site, WordPress/CMS site, ecommerce, SaaS app, portal, marketplace, media site, community site, or internal web app.
- Treat legal, tax, privacy, accessibility, and industry compliance items as mandatory review points, not legal advice.
- For WordPress/CMS delivery with AI, execute the blueprint as a flowchart/state machine with explicit sequence, decision gates, rework loops, action nodes, human approval nodes, stop/escalation nodes, and evidence before every state transition.

Baseline sequencing rule
- Normal WordPress website order is PRD baseline -> page briefs/sitemap -> Conversion/SEO/Security Applicability Matrix -> SEO architecture -> cybersecurity threat model/control matrix -> Design Artifact Strategy -> UX/UI Framework Compliance Matrix -> AI design-tool prompt package -> selected design artifact path such as Figma Make, Claude Design, JSON wireframes/specs, coded mockups, prototypes, screenshots, or hybrid -> owner review/rework/approval -> frozen design baseline -> SRD/SRS baseline -> AI task packets -> main WordPress/theme/template coding.
- Early technical constraints and SRD notes may be captured before mockups, but do not baseline the SRD or start main UI/CMS build until the Design Artifact Strategy, UX/UI Framework Compliance Matrix, AI design-tool prompt package, and approved mockups/design baseline exist or an exception is recorded. Low-fidelity wireframes are optional when the strategy proves structure another way.

Atomic task rule
- A task is "smallest indivisible" when it has one owner, one action verb, one output, and a clear done condition.
- If a task needs more than one owner to complete, split it.
- If a task can be independently reviewed, tested, or approved, keep it separate.
- If a task hides a decision, split the decision from the execution.

Task fields used below
- ID: unique task code.
- Owner: person primarily accountable for completion.
- Task: smallest action to perform.
- Done when: objective completion signal.

Non-negotiable gates
- Gate 1: A named sponsor, website owner/client approver, product manager, product owner, project manager, budget, scope boundary, and success metrics exist.
- Gate 2: An approved product requirements document (PRD) exists; privacy, security, accessibility, SEO, analytics, conversion/trust, content, support, and operations requirements are defined before design/build, with compulsory/contextual items classified in the Conversion/SEO/Security Applicability Matrix.
- Gate 3: Design Artifact Strategy, UX/UI Framework Compliance Matrix, AI design-tool prompt package, and owner-approved page mockup/design baseline package exist; individual launch-scope page/template mockups or equivalent artifacts are generated from the approved strategy and prompt, reviewed by the website owner, reworked until approved, and frozen before SRD final baseline and main WordPress/theme/template coding.
- Gate 4: An approved software requirements document (SRD/SRS) exists; the SRD translates the approved PRD, AI design-tool prompt package, and approved page mockups into architecture, WordPress template/CPT/content model, reliability, monitoring, backup, rollback, scaling, and data protection requirements.
- Gate 5: Every user-critical path has design, content, accessibility, analytics, security, QA, and support coverage.
- SEO Crawl/Compliance Gate: Before launch, AI/SEO crawls the full applicable website, checks rendered output across major browser engines where available, remediates applicable issues, and records a 90%+ SEO audit score or approved exceptions.
- Security-by-Design Gate: Before build and launch, threat model/control matrix, secure coding evidence, form/web/network/database protection, encryption/secrets handling, WordPress hardening, vulnerability scan results, and risk acceptance records exist.
- Gate 6: Launch has a rollback plan, incident owner, communications plan, and hypercare schedule.
- Gate 7: Ongoing operations have owners, cadences, dashboards, budgets, documentation, and escalation paths.
- AI Gate: If AI-assisted delivery is used, human supervision, tool permissions, task packets, run logs, and stop/escalation rules exist before AI work starts.

0A. AI-ASSISTED DELIVERY OPERATING MODEL
========================================================================

Purpose
- Use this section when AI agents perform project work under human supervision.
- AI may draft, build, test, inspect, document, and propose decisions, but accountable human role owners remain responsible for approval, risk acceptance, launch, and operations.
- AI-assisted delivery is an execution model, not a replacement for governance, PRD/SRD approval, legal review, security review, accessibility review, QA, or human product judgment.

Operating principles
- AI works from explicit task packets, not vague chat intent.
- AI follows the WordPress AI delivery flowchart for sequence, branch decisions, loops, approvals, and evidence; the current flow state must be named before execution.
- AI output is not accepted until it is reviewed against the same definition of ready, definition of done, and quality gates as human work.
- AI may propose product, design, architecture, content, code, QA, and operational changes; the accountable human owner approves decisions that affect users, risk, cost, scope, policy, or production.
- AI must record assumptions, sources, changed files, generated artifacts, commands run, tests run, unresolved risks, and requested approvals.
- AI must preserve traceability from PRD/SRD requirement IDs to AI design prompts, design, content, page mockups, code, tests, evidence, release notes, and operations documentation.
- AI must not start main WordPress/theme/template coding for user-facing pages until the Design Artifact Strategy, UX/UI Framework Compliance Matrix, AI design-tool prompt package, and owner-approved page mockup/design baseline gate are satisfied or a human approver records an explicit exception.

AI work modes
- Draft mode: AI creates research synthesis, PRD/SRD drafts, SEO architecture and compliance plans, cybersecurity threat models/control matrices, content drafts, page briefs, Design Artifact Strategies, UX/UI Framework Compliance Matrices, AI design-tool prompt packages for Figma Make, Claude Design, JSON low/high-fidelity specs, coded/static page mockups, prototypes, QA plans, runbooks, and documentation for human review.
- Build mode: AI implements code, configuration, CMS structures, metadata/schema/canonical/robots/sitemap output, redirects, secure form/admin/REST/AJAX handlers, prepared database queries, encryption/secrets controls, migrations, scripts, tests, data transformations, and documentation from approved task packets and approved design/mockup/SEO baselines.
- Verify mode: AI performs self-review, independent review, static checks, dependency scans, secret scans, SAST/DAST, targeted security tests, full-site SEO crawls, browser-rendered SEO checks, accessibility checks, security checks, performance checks, and evidence packaging.
- Operate mode: AI summarizes monitoring, triages defects, proposes hotfixes, drafts support/content updates, and prepares maintenance plans for human approval.
AI execution posture:
- Plan with intention: define the site architecture, map pages and components, choose the stack and tools, and outline user flows before implementation begins.
- Build with speed: generate page structure, draft reusable components, create boilerplate faster, and keep implementation aligned with approved PRD/SRD, mockups, SEO, security, and task-packet constraints.
- Communicate with clarity: write clearer UI copy, explain error messages clearly, write better README files, and draft cleaner documentation that a future maintainer can use.
- Refine with judgment: spot bugs and edge cases, refactor messy logic, improve readability and structure, and avoid clever code when a simpler maintainable structure works.
- Verify before handoff: create testing checklists, run applicable checks, prepare deployment steps, package evidence, and ship with clarity through release notes, rollback notes, launch status, and operations handoff.
Conversion, SEO, and security applicability rule:
- AI must create a Conversion/SEO/Security Applicability Matrix before AI design prompts, SRD finalization, build tickets, and launch checks for WordPress/CMS projects.
- Classify each item as compulsory default, contextual mandatory, not applicable, or approved exception. Contextual items become mandatory when triggered by page type, business model, data sensitivity, local intent, lead capture, ecommerce, portal/account behavior, API behavior, or approved PRD scope.
- Required items include page/template/CPT mapping, PRD/SRD/control IDs, implementation evidence, QA evidence, owner, status, and exception approver/expiry where applicable.
- AI must not fabricate reviews, ratings, local business data, case studies, team photos, credentials, maps, directions, or response-time promises.

Required AI task packet fields
- Task ID.
- Current flowchart state, previous gate, next gate/branch, and active loop if any.
- Accountable human owner.
- Goal and non-goals.
- Source artifacts and requirement IDs.
- Allowed files, systems, tools, and environments.
- Prohibited actions.
- Data handling limits.
- Expected output format.
- Acceptance criteria.
- Required checks and evidence.
- Reviewer and approver.
- Rollback, cleanup, or handoff notes.

Human supervision rules
- SP approves funding, business risk, major scope change, launch, rollback, and final go/no-go.
- PDM and PO approve PRD, product scope, backlog priority, acceptance criteria, and user-facing product decisions.
- SA approves SRD, architecture, system boundaries, major technical decisions, and technical risk acceptance.
- UX-D, UI, DS, CS, CW, BRAND, SEO, and ACC approve relevant experience, design, content, brand, search, and accessibility work.
- SEC, PRIV, DPO, LEGAL, and COMP approve relevant security, privacy, legal, compliance, data, and regulated-risk work.
- QA and AUTO approve release evidence, test coverage, regression status, and defect severity decisions.
- DEVOPS and SRE approve infrastructure, secrets, deployments, rollback, observability, production access, and incident actions.
- AI cannot be the sole approver for legal/privacy/security/accessibility risk acceptance, production deployment, destructive data operation, payment/tax/compliance decision, vendor contract decision, real-user communication, or final launch.

Mandatory AI stop/escalation triggers
- Requirements conflict or source artifacts disagree.
- Requested action exceeds approved task packet scope.
- Sensitive personal, regulated, payment, credential, or secret data may be exposed.
- Legal, tax, privacy, accessibility, security, or compliance interpretation is required.
- A destructive filesystem, database, CMS, deployment, DNS, payment, email, or production operation is requested.
- External spending, subscription changes, model/tool upgrades, or vendor changes are required.
- User-facing content, policy, pricing, claims, or transactional messaging changes without approval.
- Tests fail and the root cause is unclear.
- Pre-launch SEO crawl/audit score remains below 90% without accepted exception.
- AI detects hallucinated facts, missing evidence, or insufficient context.

AI audit trail
- Maintain an AI run log for every meaningful AI task.
- Each run log entry records task packet, agent/model/tool versions where known, prompt/context used, files changed, commands/checks run, outputs, evidence links, cost/usage if available, reviewers, approvals, unresolved risks, and next actions.
- Maintain a prompt/context library for repeatable project workflows.
- Maintain a model/tool registry showing approved AI tools, intended use, data limits, permissions, owners, and review cadence.
- Maintain a human supervision matrix showing which role must approve each class of AI-generated work.
- Maintain an AI escalation log for stop events, rejected outputs, hallucinations, policy exceptions, and lessons learned.

AI-assisted delivery gate checklist
- AI-assisted delivery policy exists.
- AI task packet template exists.
- Human supervision matrix exists.
- AI tool permission matrix exists.
- Prompt/context library exists or has a defined starter structure.
- AI run log exists and is linked from the documentation index.
- SEO crawl/compliance reference and audit evidence template exist if the project has public web pages.
- Stop/escalation rules are visible to everyone using AI.
- Sensitive data rules are documented before project data is placed into any AI context.
- Design Artifact Strategy, UX/UI Framework Compliance Matrix, and AI design-tool prompt package exist before AI-powered design artifact, JSON spec, coded mockup, prototyping, or mockup creation begins; low-fidelity wireframes are optional when the strategy proves structure another way; owner-approved page mockup/design baseline package exists before AI build-mode UI, WordPress theme, or WordPress template implementation tasks begin.
- WordPress AI flow-state checkpoint and gate evidence register exist for projects using AI-assisted delivery.

0B. WORDPRESS AI DELIVERY FLOWCHART CONTROL MODEL
========================================================================

Purpose
- Use this section when the website is a WordPress/CMS project and AI is doing substantial delivery work.
- Treat the full task checklist as the work breakdown structure and this section as the execution-control model.
- For installed Codex and Claude Code skills, load references/wordpress-ai-delivery-flowchart.md for the full Mermaid flowchart, state checklist, rework loops, and output format.

Control rule
- The AI must identify the current flow state before acting: F0 governance, F1 discovery, F2 PRD, F3 sitemap/page briefs/SEO/security architecture, F4 design artifact strategy, UX/UI framework compliance, prompt, and mockup loop, F5 SRD/SRS, F6 AI task packets, F7 WordPress/CPT build, F8 template/content/SEO implementation, F9 QA/SEO crawl, F10 UAT, F11 launch readiness, F12 deploy/stabilize, or F13 hypercare/operations.
- Every state ends in a decision: proceed, rework loop, approved exception, escalate, or stop.
- If a required earlier artifact is missing, stale, contradicted, or unapproved, return to the earliest affected state instead of continuing forward.
- AI may execute action states from approved task packets; humans approve baseline documents, AI design prompt package completeness, owner mockups, risk exceptions, production deployment, rollback, and final launch.

Normal WordPress AI execution path
- F0 Intake/governance -> F1 Discovery -> F2 approved PRD -> F3 sitemap/page briefs/applicability matrix/SEO/security architecture -> F4 Design Artifact Strategy plus UX/UI Framework Compliance Matrix plus AI design prompt package plus owner-approved mockups/design baseline -> F5 approved SRD/SRS -> F6 AI task packets -> F7 WordPress/CPT build -> F8 templates/content/SEO implementation -> F9 QA and full-site SEO crawl -> F10 UAT -> F11 launch readiness -> F12 deploy/stabilize -> F13 hypercare/operations.

Mandatory loops
- PRD loop: Rework PRD until product/sponsor approval or approved exception.
- Design artifact strategy and prompt loop: Rework the Design Artifact Strategy, UX/UI Framework Compliance Matrix, and AI design-tool prompt package until they fully map the PRD, sitemap/page briefs, SEO/cybersecurity plans, content, brand, WordPress/CPT/admin model, domain workflows, component inventory, actions, menus, widgets, states, responsive rules, accessibility, privacy, JSON/coded artifact rules, and tool constraints before selected artifact execution.
- Mockup/design baseline loop: Rework AI-generated individual page/template mockups or equivalent JSON/coded/design artifacts, with UX/UI Framework Compliance Matrix evidence, until website-owner approval or approved page-level exception; main WordPress/theme/template coding remains blocked for unapproved pages/templates.
- SRD loop: Rework SRD/SRS until it matches the approved PRD, AI design prompt package, mockups, SEO architecture, CPT model, and risk controls.
- CPT loop: Rework any project CPT that opens the block builder by default or lacks required custom metadata/media fields.
- SEO loop: Remediate crawl/audit findings and rerun checks until the SEO audit target is 90%+ or an accountable human approves an exception.
- QA/UAT loop: Fix or route defects through change control, then rerun affected checks and acceptance scenarios.
- Launch loop: If go/no-go is no-go, fix blockers and rerun launch readiness; if production verification fails, hotfix or rollback under human control.
- Operations loop: Route recurring defects, SEO/indexing issues, support confusion, or improvement opportunities through change control and a new release cycle.

Flow-state reporting requirement
- Every AI plan, audit, rescue, handoff, or status report must state the current flow state, completed gates, blocked gates, active loop, required human decision, AI actions allowed now, evidence required before the next state, and next branch.

0C. CYBERSECURITY BY DESIGN CONTROL MODEL
========================================================================

Purpose
- Use this section across the entire project lifecycle, especially during WordPress coding and configuration.
- Treat cybersecurity as a build requirement and launch gate, not a final optional scan.
- Use OWASP Top 10, OWASP ASVS, OWASP Web Security Testing Guide, OWASP Cheat Sheet Series, WordPress hardening guidance, and NIST CSF 2.0 as reference baselines, scaled to project risk.

Lifecycle security rule
- Discovery identifies assets, data, users, roles, entry points, trust boundaries, integrations, hosting/network exposure, and abuse cases.
- PRD records user-facing and business-level security requirements.
- AI design prompts, page briefs, sitemap, mockups, and SRD/SRS carry security implications for every form, account flow, admin action, CPT, upload, integration, and data store.
- AI task packets include threat-model/control IDs, protected assets, sensitive data limits, required checks, and security evidence.
- Coding tasks are not done until applicable security controls are implemented and tested.
- QA and launch readiness include dependency scans, secret scans, static analysis, dynamic testing, targeted manual tests, WordPress hardening verification, database/backup checks, network/WAF checks, and risk acceptance.
- Operations include vulnerability monitoring, patching, WAF/rate-limit review, log review, backup restore testing, incident response, and security debt management.

Coding-phase security rule
- Prevent SQL injection with prepared statements/parameterized queries, `$wpdb->prepare()` for WordPress custom queries, allowlists for dynamic identifiers, and least-privilege database users.
- Validate all external input server-side and escape all output for the exact output context.
- Protect state-changing browser actions with CSRF tokens or WordPress nonces and never mutate state through GET requests.
- Enforce authentication, MFA for privileged users, secure session behavior, and server-side authorization/capability checks for every protected action.
- Protect forms with spam/bot controls, rate limiting, safe errors, privacy/consent handling, duplicate/idempotency rules, and abuse monitoring.
- Protect uploads with allowlisted types, size limits, safe names, storage rules, malware scanning where feasible, and no public execution of uploaded files.
- Protect web/network surfaces with TLS, security headers, CSP where feasible, WAF/CDN/rate limits, admin restrictions, staging protection, and public debug disabled.
- Protect databases and stored data with least privilege, safe migrations, backups, restore tests, retention/deletion rules, encrypted backups or accepted exceptions, and no database errors exposed to users.
- Protect secrets and encryption keys by storing them outside code, rotating when needed, masking logs, and never exposing secrets to AI context, frontend bundles, browser sessions, or public artifacts.

Security launch gate
- Launch cannot proceed with unresolved critical/high security findings, known SQL injection paths, broken authorization, exposed secrets, missing required encryption, unsafe uploads, unprotected admin access, failed form-abuse controls, broken backup/restore, or unreviewed WAF/network exposure unless an accountable human records accepted risk, compensating controls, and expiry.

3. PHASE 0 - PROJECT INITIATION AND MANDATE
========================================================================

Objective
- Establish why the project exists, who can decide, what success means, and what boundaries cannot be crossed.

Atomic tasks
- P0.001 | SP | Name the executive sponsor | Done when one sponsor is documented.
- P0.002 | SP | Name the product manager | Done when one accountable PDM is documented.
- P0.002A | SP | Name the product owner | Done when one accountable PO is documented.

22. "DO NOT MISS" CROSS-CUTTING EDGE CASES
========================================================================

User experience edge cases
- First visit.
- Returning visit.
- Logged out.
- Logged in.
- Expired session.
- Forgotten password.
- No search results.
- Empty cart.
- Payment failure.
- Duplicate form submission.
- Slow network.
- Offline or interrupted connection.
- File too large.
- Unsupported file type.
- Permission denied.
- Account locked.
- User wants to delete account.
- User wants to change consent.
- User uses keyboard only.
- User uses screen reader.
- User uses high zoom.
- User prefers reduced motion.
- User has low bandwidth.
- User is on mobile with one hand.
- User changes language.
- User changes currency.
- User arrives through old URL.
- User arrives through ad with tracking blocked.
- User opens email link after token expired.
- User need conflicts with a business, compliance, or technical requirement.

Operational edge cases
- DNS provider is unavailable.
- Payment provider is degraded.
- Email provider is blacklisted or rate limited.
- CRM API is down.
- CMS admin is inaccessible.
- Search provider is stale.
- CDN caches wrong content.
- Backup job silently fails.
- Staging site becomes indexed.
- Developer commits secret.
- Plugin update breaks checkout.
- Editor deletes important page.
- Bot floods forms.
- Account credential stuffing begins.
- Social campaign creates traffic spike.
- Legal asks for urgent policy update.
- Customer requests deletion while order retention applies.
- Vendor contract auto-renews unexpectedly.
- Key employee leaves.
- Domain renewal is missed.
- SSL certificate renewal fails.
- Requirement changes after PRD, design, architecture, QA, or launch baseline.
- PRD or SRD owner leaves before approval or handoff.

Out-of-the-box resilience ideas
- Create a one-click "disable risky feature" kill switch for payments, AI, search, forms, or chat.
- Add "known issue" content blocks support can activate without a developer.
- Maintain a plain static emergency page that can be served if the app is down.
- Practice a "fake launch" one week before launch with all real people and timing.
- Run a "staging leak drill" to verify staging cannot be indexed or accessed publicly.
- Run an "editor disaster drill" where a page is accidentally deleted and restored.
- Run a "vendor outage drill" for CRM, payment, email, or search.
- Run a "privacy request drill" to export/delete a test user's data.
- Add a "data nutrition label" for each form: why each field is collected and how long it is kept.
- Add a "third-party script budget" requiring approval for every new external script.
- Maintain a "graveyard list" of removed pages, features, vendors, plugins, and reasons.
- Track "user trust debt" separately from technical debt.
- Maintain a requirements decision ledger linking PRD/SRD changes to backlog, tests, approvals, release notes, and support documentation.

25. CLOSING NOTE
========================================================================

This blueprint is intentionally broad. No single project should execute every optional task blindly.
The correct use is to mark each task as:
- Required now
- Required later
- Not applicable
- Requires specialist review
- Accepted risk

The strongest teams do not treat launch as the finish line. They treat launch as the start of measured operations.
If AI assists delivery, the strongest teams also treat every AI output as supervised work product: traceable, reviewed, tested, approved, and continuously improved.
