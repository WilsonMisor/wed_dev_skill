## 14.1 Risk Runtime Concern Separation and Linked Normalisation

Do not force `RiskDefinition`, `RiskAssessment`, `RiskEconomics`, `RiskEvolution`, `RiskEvidence` and `RiskAcceptance` into one monolithic flat record merely to preserve a historical document format.

Inspect PREOS's existing schemas first.

Where PREOS already separates these concerns, preserve that separation.

Where they remain embedded in one object, determine whether normalisation into separately addressable but linked records improves lifecycle, evidence freshness, versioning, queryability, and change-impact analysis.

At minimum, the runtime model must make the following concerns independently versionable or independently addressable:

1. immutable/reusable risk definition;
2. application/release-specific assessment;
3. economics and complexity assessment;
4. evolution/deferral/activation decision;
5. evidence set and freshness state;
6. risk acceptance and authority record.

Do not introduce unnecessary schema fragmentation if the existing PREOS model already provides equivalent boundaries.

### 14.1.1 Implementation Requirements

The implementation must preserve the semantic separation of these concerns even if PREOS chooses to store some of them in the same physical document, database table, JSON object family, or aggregate for performance or compatibility reasons. Logical independence is mandatory; physical fragmentation is not.

1. `RiskDefinition` must represent reusable, project-independent knowledge and must not acquire release-specific status, evidence freshness, temporary mitigations, or human acceptance decisions.
2. `RiskAssessment` must bind a risk definition to a specific project, application, feature, task packet, branch, environment, release, or other governed assessment scope.
3. `RiskEconomics` must make cost, unit economics, complexity tax, failure cost, cost concentration, and architecture-economic assumptions independently inspectable and refreshable without mutating the canonical risk definition.
4. `RiskEvolution` must make maturity stage, deferral status, activation trigger, migration path, review condition, and architecture-evolution decisions independently inspectable and refreshable.
5. `RiskEvidence` must make evidence artifacts, evidence bindings, freshness, invalidation conditions, provenance, integrity hashes, verification state, and evidence history independently inspectable and refreshable.
6. `RiskAcceptance` must make accepting authority, scope, rationale, residual risk, compensating controls, approval timestamp, expiration, review trigger, and revocation state independently inspectable and must never be inferred from an AI-generated status.
7. Link the concerns through stable identifiers and explicit relationships rather than by duplicating entire records across objects.
8. Preserve referential integrity so that no assessment, economics record, evolution decision, evidence set, or acceptance record can silently reference a missing or superseded risk definition.
9. Preserve historical versions where required for auditability. A later risk-definition update must not silently rewrite the historical meaning of an earlier release assessment or acceptance decision.
10. Define change-impact rules so a change to one concern invalidates or re-evaluates only the dependent concerns that actually require reconsideration.
11. Evidence invalidation must not require rewriting the canonical risk definition.
12. Expiration or revocation of risk acceptance must not require rewriting the canonical risk definition.
13. Architecture or cost changes must be able to refresh economics/evolution state without manufacturing a new canonical risk solely because deployment economics changed.
14. A risk-definition semantic correction must trigger explicit impact analysis against linked assessments, evidence, controls, acceptances, ADRs, deferred-complexity records, tests, and release decisions.
15. If PREOS already implements equivalent boundaries under different object names, preserve the existing canonical names and create a documented semantic crosswalk rather than creating duplicate parallel object types.
16. If PREOS intentionally uses an aggregate model, document how each of the six concerns remains independently addressable, independently queryable, independently versionable where required, and independently invalidatable where required.
17. Do not normalize merely for theoretical database purity. The chosen model must improve or preserve lifecycle safety, evidence freshness, versioning, queryability, change-impact analysis, and compatibility.
18. Do not denormalize merely to preserve the historical 37-field or 40-field source-document layout. Historical layouts remain provenance/input formats, not mandatory runtime storage architecture.

### 14.1.2 Required Validation and Acceptance Evidence

Create deterministic validation proving the chosen runtime model satisfies the concern-separation requirement. At minimum verify:

1. a canonical risk definition can exist without a project/release assessment;
2. multiple assessments can safely reference the same canonical risk definition;
3. evidence can become `STALE`, be replaced, or be invalidated without changing the canonical risk definition;
4. a risk-acceptance record can expire or be revoked without changing the canonical risk definition;
5. economics can be recalculated after workload, vendor price, architecture, or scale changes without changing unrelated immutable risk knowledge;
6. an evolution/deferral activation trigger can be reached and updated without corrupting historical assessments;
7. historical release evidence and acceptance remain traceable to the version of the risk definition and other source state against which they were evaluated;
8. orphan references are rejected;
9. duplicate parallel models are detected where an existing PREOS model already provides the same boundary;
10. source 37-field and 40-field records can be transformed into the richer model without data loss and without forcing all runtime concerns back into one flat record.

Record the resulting design decision, schema crosswalk, migration behavior, validation results, and any intentional aggregate-storage decision in the recommendation compliance register and final migration report.
